# Execution boundaries and limitations

Node execution uses a dedicated process, not node:vm. Stop kills its process tree on Windows with taskkill and its process group on Unix. This is a stability boundary, **not a sandbox for hostile code**. Node scripts can read/write files, connect to the network and launch processes with the current user's permissions, including reading accessible credential files. Deliberately detached child processes can escape process-group cleanup on Unix; malicious code requires a separately configured OS/container sandbox. Do not execute untrusted snippets.

The application renderer has contextIsolation, sandbox and no nodeIntegration. Preload exposes named typed operations. Every privileged IPC request checks both the main renderer identity and its main frame and validates its arguments. Browser preview is a distinct WebContentsView in a separate session with nodeIntegration off, contextIsolation and Chromium sandbox on, denied permissions/popups/navigation, and no privileged app bridge. Its only preload endpoint submits untrusted console snapshots. Browser networking is still available; imported web content and scripts can make requests.

Node inherits only basic operating-system environment paths and explicitly configured tab variables, not the app's credential environment. This is not a filesystem permission barrier. Variables are stored with Electron safeStorage when secure OS-backed storage is available; insecure Linux basic_text is rejected. Otherwise they live only in memory. The environment editor displays configured values to its user. Explicit logs can reveal them; no automatic environment dump exists.

Defaults: 30-second context lifetime, Node V8 heap 256 MB, 500 output records, 100 inspection entries and depth 5. Preferences allow changes and disabling lifetime (0). Heap size is not a total process memory cap. Binary buffers/native allocations and Browser memory are not limited by it. Set a finite lifetime for potentially blocking browser code. Each log takes a bounded descriptor snapshot, never invoking getters; proxy traps can execute and are contained in the disposable runtime. Exception stack collection is separate from value inspection and can access the thrown Error's stack. Values are snapshotted, not live handles. Raw stdout/stderr is drained and bounded separately.

Package installations use structured npm arguments without a shell. Scripts are disabled by default; the user must enable them explicitly for an operation. Enabling scripts grants installed package code the install process's user permissions. Packages are untrusted even when install scripts are disabled: imported modules execute code. npm honors normal registry configuration. No telemetry, automatic code upload, mandatory account or cloud dependency is present. Optional AI requests occur only after the user explicitly clicks Generate code. See [AI privacy and credentials](ai-provider.md).

Combined Browser + Node design: RunJS documents simultaneous DOM and Node globals. Achieving that with Electron nodeIntegration would remove Chromium process sandboxing and would require a dedicated execution application/process, sanitized environment, separate session, no privileged preload and verified lifecycle/IPC boundaries. A Node DOM emulation would have different Canvas, layout and WebGL semantics and is not equivalent. Version 0.1 therefore exposes only the two tested runtimes. A combined runtime must pass the same cancellation, environment-leak and bridge-isolation tests before exposure.

Both runtimes also enforce fixed transport ceilings (180 KB per snapshot and 4 MB per run) with visible truncation. The npm subprocess uses the same basic environment allowlist; registry credentials may still be supplied explicitly through npm configuration.


## Python and reference links (0.2)

Python snippets have full user permissions just like Node. The interpreter is user-installed and may be a chosen virtualenv executable. The app launches it with structured arguments, a restricted inherited environment, explicit tab overrides and no shell. Timeout and output protections apply; the Node memory setting does not limit Python. No Python heap cap or hostile-code sandbox is provided. Deliberately detached children remain outside the process-tree cleanup guarantee. Reference links are catalog IDs resolved in main, never arbitrary renderer URLs; opening them is explicit and code is not sent.

## C# and .NET (0.3)

C# uses a temporary SDK project with cleared NuGet sources and disabled shared build servers. Compilation and execution run in separate cancellable processes with a basic environment allowlist, required OS directory variables, and explicit tab overrides. .NET CLI telemetry is disabled. SDK framework reference packs must be installed for offline compilation. User C# code has user permissions and can still access the network; there is no C# memory cap or hostile-code sandbox. Output is bounded text and compiler/runtime source lines are parsed from diagnostics.

The documentation website contains only public guides and original examples. It never receives desktop snippets or environment variables. Its Markdown comes from reviewed repository files, raw HTML is escaped, and search input is never evaluated as HTML. Clipboard writes happen only after a click.
